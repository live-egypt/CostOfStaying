# MVP Acceptance Criteria — v2.1
**الحالة: PROPOSED**

لا يعد MVP مكتملاً حتى تتحقق البنود التالية:

## Gameplay
- مباراة لأربعة لاعبين تبدأ وتنتهي دون تدخل المطور.
- Vitality تبدأ عند 100 وتتآكل وفق معدل خادمي؛ الموت عند الصفر.
- Collapse يزيد التآكل ويطبق Debuff.
- Transfer ينقل آخر Debuff كاملاً (Move لا Copy) بمعاملة ذرية.
- Betrayal يحسب بعد النقل الناجح فقط، ولا يمنح نقاط فوز.
- Spirit محايد، يجمع Echo Fragments ولا يؤثر مباشرة في صحة الأحياء أو مواقعهم.
- تصويت 3 أحياء يتطلب إجماعاً لإنهاء المباراة جماعياً.
- نتائج Last Survivor وCollective Surrender وTime Limit وMutual Collapse واضحة.

## Networking
- الخادم يملك الحالة ويحسب جميع النتائج الحساسة.
- اتصال لاعبين على جهازين مختلفين ثم اختبار أربعة لاعبين.
- معالجة disconnect/reconnect وفق سياسة معتمدة.
- لا يسبب replay أو RPC spam تغييراً غير مشروع للحالة.

## Stability and Performance
- لا crash أو فساد حالة معروف في سيناريو الاختبار الكامل.
- أداء Android مقاس على أجهزة من الفئة المستهدفة مع تقرير قابل للتكرار.
- أداء الخادم مقاس عند أربعة لاعبين مع هامش CPU/RAM موثق.
- لا توجد ميزانية أداء معلنة بلا baseline.

## Security
- لا أسرار في Git أو العميل.
- لا Critical/High findings مفتوحة دون قبول مخاطر مكتوب.
- اختبارات regression للأخطاء الأمنية المكتشفة.
- سجلات الحوادث لا تحتوي أسراراً أو بيانات شخصية غير لازمة.

## Delivery Evidence
لكل بند: Requirement ID، test ID، commit SHA، artifact hash، بيئة الاختبار، النتيجة، وتاريخ التحقق. لا تحول الحالة إلى VERIFIED دون إرفاق الدليل.
