# Data Architecture — v2.1
**الحالة: PROPOSED | الحفظ الدائم يتبع ADR-003**

## مبدأ التصميم
لا تنشئ قاعدة بيانات ولا تحفظ كل tick. حالة المباراة الحية داخل ذاكرة Dedicated Server. البيانات الدائمة لا تُضاف قبل اعتماد مزود في ADR-003.

## تصنيف البيانات المقترح
| النوع | أمثلة | التخزين المقترح | الملاحظة |
|---|---|---|---|
| Match Runtime | Vitality، Debuffs، المؤقتات، الذخيرة، التصويت | ذاكرة الخادم | تنتهي بانتهاء المباراة |
| Match Result | نوع النتيجة وفق RULE-05، المدة، إصدار القواعد | Backend عند اعتماده | الأنواع معرّفة في القواعد؛ الحفظ غير معتمد |
| Account | معرف الحساب، الاسم، إعدادات | Backend عند الحاجة | الحد الأدنى فقط؛ خارج MVP الحالي |
| Operational Telemetry | crash، tick time، disconnect | نظام مراقبة | لا أسرار ولا PII غير لازمة |
| Security Events | replay وRPC abuse | سجلات محمية | سياسة الاحتفاظ TBD |

## قواعد الاتساق
- الخادم هو مصدر الحقيقة لحالة المباراة وفق ADR-002.
- لا يعتمد العميل على تخزين محلي لنتيجة موثوقة.
- استخدم MatchId عشوائياً ومعرفات أحداث فريدة.
- أحداث النقل والضرر والتصويت تطبق مرة واحدة منطقياً.
- لا تحفظ Snapshot مستمراً إلا إذا أثبت تصميم الاستعادة الحاجة واعتمدت سياسة إعادة الاتصال.

## قرارات معلقة
مزود Backend، مخطط الحساب، مدد الاحتفاظ، منطقة البيانات، الحذف والتصدير، واستعادة المباراة بعد تعطل الخادم.

## القبول
كل حقل دائم يجب أن يحدد الغرض والمالك والحساسية والمصدر ومدة الاحتفاظ ومن يقرأه أو يعدّله قبل أي حفظ إنتاجي.
