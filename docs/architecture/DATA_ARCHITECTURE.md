# Data Architecture — v2.0
**الحالة: PROPOSED**

## مبدأ التصميم
لا تنشئ قاعدة بيانات أو تحفظ كل tick. حالة المباراة الحية داخل ذاكرة Dedicated Server، أما البيانات الدائمة فتقتصر على ما يحتاجه المنتج فعلياً.

## تصنيف البيانات المقترح
| النوع | أمثلة | التخزين المقترح | الملاحظة |
|---|---|---|---|
| Match Runtime | الصحة، Debuffs، المؤقتات، الذخيرة، التصويت | ذاكرة الخادم | تنتهي بانتهاء المباراة |
| Match Result | الفائز/النتيجة، مدة المباراة، إصدار القواعد | Backend عند اعتماده | لا يخزن قبل تعريف نتيجة المباراة |
| Account | معرف الحساب، الاسم، إعدادات | Backend عند الحاجة | الحد الأدنى فقط |
| Operational Telemetry | crash، tick time، disconnect | نظام مراقبة | لا يتضمن أسراراً أو PII غير لازمة |
| Security Events | محاولات replay وRPC abuse | سجلات محمية | سياسة الاحتفاظ TBD |

## قواعد الاتساق
- الخادم هو مصدر الحقيقة لحالة المباراة.
- لا يعتمد العميل على تخزين محلي لنتيجة موثوقة.
- استخدم MatchId عشوائياً ومعرفات أحداث فريدة.
- أحداث النقل والضرر والتصويت تطبق مرة واحدة منطقياً (idempotent).
- لا تحفظ Snapshot مستمر إلا إذا أثبتت ميزة reconnect/restore الحاجة إليه.

## قرارات معلقة
Backend provider، مخطط الحساب، مدد الاحتفاظ، منطقة البيانات، حذف/تصدير البيانات، وسياسة استعادة المباراة بعد تعطل الخادم.

## القبول
يجب أن يحدد كل حقل: الغرض، المالك، الحساسية، المصدر، مدة الاحتفاظ، ومن يحق له قراءته أو تعديله.
